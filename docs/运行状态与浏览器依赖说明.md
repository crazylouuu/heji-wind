## 三、是否依赖浏览器后台进程

### 结论：**前端依赖 WebView2，后端完全不依赖**

这是两个独立的部分，必须分开看：

| 部分 | 是否依赖浏览器内核 | 说明 |
| --- | --- | --- |
| **前端界面**（Vue 3 + 工具箱页面 + 合迹实验记录页） | ✅ **强依赖 WebView2** | Tauri 在 Windows 上只用 WebView2 作为渲染引擎，没有替代方案 |
| **后端服务**（FastAPI + SQLite） | ❌ **完全不依赖** | 纯 Python 进程，无浏览器、无 Node、无 Electron |

**关键证据（本次实测）**：主壳启动后**没有产生任何 `msedgewebview2.exe` 子进程**
（因为窗口没创建出来），但后端依然完整可用、11 项功能全部通过。
→ 证明后端与浏览器内核无关，只有界面渲染才需要它。

### "浏览器后台进程"具体指什么

不是 Chrome/Edge 浏览器本身，而是 **Microsoft Edge WebView2 Runtime**：

- 本机已安装，版本 **155.0.4283.62**（`HKLM:\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate`）
- Windows 10/11 通常预装；Windows 7/8 需单独装（微软官方免费）
- 它是**被应用按需加载的组件**，不是常驻后台服务
- 应用不会启动 `msedge.exe`（那是你日常用的浏览器，与本应用无关）

### 进程模型

应用启动后会产生一棵这样的进程树：

```
heji-toolbox.exe                 ← 主壳（Rust，几十 MB）
├── ChemLabBackend.exe           ← Python 后端（本次实测 30~106MB，随查询增长）
└── msedgewebview2.exe (browser) ← WebView2 主进程（窗口创建时才有）
    ├── msedgewebview2.exe (renderer)  ← 渲染进程（跑 Vue 页面）
    ├── msedgewebview2.exe (gpu)       ← GPU 加速进程
    └── msedgewebview2.exe (utility)   ← 网络/存储等辅助进程
```

WebView2 采用 Chromium 的多进程架构，进程数量随页面数量增长。

### 触发场景（什么时候会拉起浏览器进程）

| 场景 | 是否创建 WebView2 | 说明 |
| --- | --- | --- |
| **应用启动、主窗口显示** | ✅ 必然创建 | 整个前端界面都在 WebView2 里渲染 |
| 打开「实验记录」页（原生子 webview 通道） | ✅ 再建一个渲染环境 | 第二个 webview 加载合迹前端，独立进程 |
| 打开「实验记录」页（iframe 兼容模式） | ⭕ 复用主窗口内核 | iframe 在同一个 WebView2 里，不额外建进程 |
| 最小化 / 窗口被遮挡 | ⭕ 进程保留但降频 | Chromium 的后台节流：不可见时降低渲染与定时器频率 |
| 关闭主窗口 | ❌ 全部退出 | WebView2 进程随主壳销毁 |
| 只跑后端（不走界面） | ❌ 不创建 | 例如脚本直接调 API |

| 关注点 | 结论 |

## 五、启动耗时：首次启动明显更慢（不是故障）

排查过程中曾出现一次「主壳起来了但后端没起」的现象，**结论是首次冷启动超时，不是缺陷**。
以下是完整的实测数据与排除过程，留作记录，避免以后再误判。

### 实测启动耗时（同一台机器，连续 4 次）

| 次序 | 后端就绪耗时 | 说明 |
| --- | --- | --- |
| 第 1 次（冷启动） | **> 18 秒**（观察窗内未就绪，曾误判为失败） | 杀软首次扫描 190MB 的 sidecar 目录 + 磁盘冷读 |
| 第 2 次 | **13 秒** | 文件已进系统缓存 |
| 第 3 次 | **7 秒** | |
| 第 4 次 | **7 秒** | 稳定在 7 秒左右 |

**为什么首次慢**：sidecar 是 PyInstaller onedir 产物（`_internal` 189MB），
第一次启动时 Windows Defender 要完整扫描这批文件，同时磁盘是冷读。
文件被扫描过并进入缓存后，速度稳定在 7 秒左右。

**主壳的行为**：等待上限 **25 秒**。超时不会崩溃，只是状态里带 `error`，
前端会显示「后端未就绪」。下次启动通常会恢复正常（文件已被扫描）。

### 已排除的假设（全部经实验证伪）

| 假设 | 验证方式 | 结果 |
| --- | --- | --- |
| `sidecar_path()` 找不到 `resources/backend` 候选 | 新增 3 个单元测试，用临时目录造两种布局 | ✅ 逻辑正确，两种布局都能命中 |
| 构建目录的资源布局与安装版不同导致失败 | 从 `target/release` 直接启动（sidecar 在 `resources/backend`） | ✅ 连续 3 次成功拉起 |
| sidecar 二进制损坏 | 手动直接运行 `--port 8799` | ✅ 正常（health 200） |
| 日志目录不可写 | 检查 `%APPDATA%\com.heji.toolbox\logs` | ✅ 可写 |

### 副产品：新增启动诊断日志

排查时发现一个真实的可观测性缺口——**打包版是 GUI 子系统，没有控制台**，
`println!` 的输出看不到，而 `start()` 的失败分支只把原因写进内存里的
`status.error`。一旦窗口没起来，失败原因就彻底不可见。

已补上 `backend::write_startup_log()`，每次启动写一份
`%APPDATA%\com.heji.toolbox\logs\startup.log`：

```

resource_dir   = \\?\D:\...\target\release
backend_dir    = \\?\D:\...\target\release\backend

running        = true
base_url       = http://127.0.0.1:8765
pid            = Some(332)
reused         = false

```

以后遇到「应用开着但后端不启动」，先看这个文件，比翻代码快得多。

## 六、快速自检清单

> ⚠️ **前提：应用必须先启动。**
> `http://127.0.0.1:8765` 是**应用内部的后端服务**，不是常驻的系统服务。
> 应用没开 → 端口不监听 → 浏览器必然显示「无法访问此网站」。这是正常现象，不是故障。
>
> **更进一步：这个服务是应用自己创建的，不是预先存在的。**
> 双击图标 → 主壳启动 → 主壳拉起子进程 `ChemLabBackend.exe`（带参数 `--port 8765`）
> → 子进程开始监听 → 界面通过该地址与它通信。
> 所以不存在「你需要先安装/启动某个服务」「你需要配置服务器地址」这类准备工作。
>
> 可以实测验证这个父子关系（父进程 ID 必然等于主壳 PID）：
> ```bat
> wmic process where "name='ChemLabBackend.exe'" get ProcessId,ParentProcessId,CommandLine
> ```
> 应看到命令行带 `--port 8765`，且 `ParentProcessId` 与主壳 PID 一致。
>
> 正确顺序：**先双击桌面「合记 ChemLab」→ 等 7~25 秒（首次更久）→ 再访问这个地址。**

### 第一步：确认应用在跑

```bat
tasklist | findstr /i "heji-toolbox ChemLabBackend"
```

应看到两个进程：`heji-toolbox.exe`（主壳）与 `ChemLabBackend.exe`（后端）。
**一个都没有 → 应用没启动**，去双击桌面图标。

### 第二步：确认端口在听

```bat
netstat -ano | findstr 8765
```

应有一行 `TCP 127.0.0.1:8765 ... LISTENING`。
如果只有 `TIME_WAIT` 没有 `LISTENING`，说明后端刚退出过，重新启动应用。

### 第三步：确认接口正常

浏览器打开 `http://127.0.0.1:8765/api/health`，应返回：

```json
{"status":"ok","service":"ChemLab","version":"0.1.0-integ",
 "code_fingerprint":"bc2aa996d22bd97a","disk_fingerprint":"bc2aa996d22bd97a"}
```

各字段含义：

| 字段 | 含义 | 怎么判断正常 |
| --- | --- | --- |
| `status` | 服务状态 | 必须是 `ok` |
| `service` | 服务标识 | 必须是 `ChemLab`（主壳靠它防止误连旧版 ChemELN） |
| `version` | 后端版本 | `0.1.0-integ` 是当前整合版 |
| `code_fingerprint` | **运行中进程**的代码指纹 | 与下一项**相等**才正常 |
| `disk_fingerprint` | **磁盘上代码**现算的指纹 | 两者不等 = 跑的是旧代码，需重启应用 |

### 第四步：看界面

应用「设置 → 后端服务」卡片 → 显示「运行中」+ 地址 + PID + 版本。
