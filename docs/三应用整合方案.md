- 合成工具箱：Rust 侧 `rusqlite::Connection` 持有 Mutex 全局单例，`app.manage(db::Db(Mutex::new(conn)))`，命令经 `State<Db>` 取用。**同步阻塞模型，无 HTTP 层**。

### 2.2 status 枚举冲突（三套互不相同）

| 应用 | 取值 |
| --- | --- |
| 黄河 | `draft`（默认）/ 其他 |
| 合迹 | `draft` / `ongoing` / `completed` / `archived` |
| 工具箱 | `planned` / `running` / `finished` / `aborted` |

**归一映射建议**（以合迹的 4 态为基准，因为它最完整且是主力应用）：

| 黄河 | 工具箱 | → 归一值 |
| --- | --- | --- |
| `draft` | `planned` | `draft` |
| — | `running` | `ongoing` |
| — | `finished` | `completed` |
| — | `aborted` | `archived`（或新增 `aborted` 态） |

建议在归一表中**保留 `aborted` 作为第 5 态**——工具箱已有此语义，映射成 `archived` 会丢失信息。

**关键发现**：黄河的 `materials` 是**库房管理表**（有供应商/批号/存放位/纯度），合迹的 `compounds` 是**化学实体表**（有 InChI/Molfile）。这是**语义差异**而非简单改名。

**归一策略**：合并为 `compounds` 统一表，保留全部字段（超集），并：
- `mol_weight` → `mw`（改名）
- `note` → `notes`
- 黄河 256 条按 CAS 去重导入，`supplier/batch_no/location` 允许一行多值 → **建 `compound_sources` 附属表**存批次信息
- `category` 取值域扩展为 `solvent|reagent|project|material|general`

### 3.2 重复度量化

| 层面 | 重复内容 | 估算重复率 |
| --- | --- | --- |
| **前端框架** | Vue 3.5 完整实现 vs 原生 JS 完整实现 | **~100% 互斥**（无法复用代码） |

| **导出逻辑** | PDF/Excel/JSON 导出各写一遍 | **~40% 重复** |

**结论**：
- **代码复用天花板不高** —— 前端技术栈完全互斥（Tauri-Vue vs 原生 JS），无法直接合并源码

- **架构复用可行** —— 工具箱的 Tauri 壳 + 合迹的 FastAPI 后端可以组合

## 第四部分：整合方案

### 4.1 路径对比：为什么推荐「壳聚合 + 数据归一」

| 维度 | A. 代码级合并（重写为单一 Tauri+Vue 应用） | **B. 壳聚合（Tauri 主壳 + 内嵌服务）** ✅ | C. 统一入口（桌面快捷方式/启动器） |
| --- | --- | --- | --- |
| 做法 | 把合迹/黄河的 Python 后端用 Rust 重写，前端迁到 Vue | Tauri 主程序内嵌 Python 后端子进程，前端做统一导航 | 只做一个启动器，同时拉起两个应用 |
| 工作量 | **极大**（12~18 人日） | **中**（5~8 人日） | **小**（1~2 人日） |
| 技术风险 | **极高**（RDKit 无 Rust 等价库，Ketcher 嵌入复杂，PDF/DOCX 导出要重写） | 中（子进程管理、端口、生命周期） | 低 |
| 交付形态 | 单一 exe | 单一安装包（内含 Python 运行时） | **仍是 2~3 个程序**，问题未根治 |
| 用户体验 | 最佳 | 好（一个窗口统一导航） | 差（还是多个窗口/浏览器页） |
| 数据统一 | 天然统一 | **可做（同一 DB）** | 做不到 |
| 功能完整度 | 有丢失风险（Python 特有能力重写难） | **100% 保留** | 100% 保留 |
| 长期维护 | 单一技术栈，最清爽 | 双栈但边界清晰 | 三份代码各自维护 |

**推荐 B**，理由：
1. **RDKit 是硬约束** —— Python 侧化学能力（SMILES 解析、子结构检索、InChIKey、试剂表自动计算、2D 结构渲染）无成熟 Rust 等价物。强行 Rust 化 = 功能缩水。
2. **Ketcher 是前端重灾区** —— 它是 React 应用，嵌入 Vue 壳需要 iframe 桥接或改写，成本高收益低。
3. **导出链复杂** —— xhtml2pdf / python-docx / openpyxl / beautifulsoup4 的组合在 Python 里已经调通，Rust 重写 PDF+Word 导出会引入大量回归风险。
4. **工作量与收益比** —— B 只需统一「壳」和「数据」，不动已跑通的业务逻辑。
5. **顺带解决安全问题** —— 路径 C 无法把 chemELN 后端收进桌面壳内，也就无法统一做「绑 127.0.0.1 + token 鉴权」的加固（见 R0）。路径 B 天然提供了这个收口位置。

**同时建议：B 落地后，把 C 作为过渡**（阶段 0），先解决"三份安装、三种启动"的混乱。

### 4.4 共享代码与公共模块抽取

**原则：单一实现源，其余调用方通过接口访问。**

| 公共模块 | 唯一实现位置 | 工具箱调用方 | 合迹调用方 | 抽取方式 |
| --- | --- | --- | --- | --- |
| **摩尔/当量/收率** | `src/utils/calc/`（TS） | 直接 import | HTTP `/chem/calc/*` | 以工具箱 18 函数为准，Python 侧 `chem.py:calculate_reagent_table` 改为**调 TS 服务**或保持算法一致但**单测对齐** |
| **溶剂物性 98 种** | `assets/data/solvents.json` | import JSON | Python 读同一 JSON | **单一 JSON 文件**，TS 直接 import，Python `json.load` |
| **试剂→MW 查表** | `assets/data/reagents.json` | import | Python 读同一 JSON | 从合迹 `common_reagents.py` 导出为 JSON（含 MW），TS 侧建索引 |
| **SMILES/结构** | Python RDKit | — | `/chem/*` | **保留在 Python**，TS 通过桥调用 |
| **SOP 渲染** | `src/utils/sop/`（marked+js-yaml） | 直接 import | 可选暴露 `/chem/sop/render` | 工具箱现有实现为准 |
| **设置/偏好** | 统一 `settings` 表 | `settings.ts` | Python 读写同一表 | 共用 `key/value` 结构（本就一致） |
| **备份/导出** | Rust 主进程 | Tauri 插件 | `/chem/export/*` | 统一由 Rust 调度 Python |

**关键：溶剂与试剂数据必须落成 JSON/CSV 单一文件**，这是最容易做且收益最直接的一步 —— 目前两处各维护一份，改一边就不同步。

    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    name       TEXT DEFAULT '',

    cas        TEXT DEFAULT '',

**其余表**：
- `projects`（黄河的 1 条项目 + 合迹的 project 文本去重后建表）
- `reagents` / `reactions` / `templates` / `tags` / `experiment_tags` / `attachments` / `versions` / `experiment_links` —— **合迹独有，直接整体迁入**，仅需加 `source_app` 字段
- `experiment_steps`（工具箱）→ 与合迹 `reagents`/`reactions` 并存，**不合并**（语义不同：前者是勾选清单，后者是结构化试剂投料）
- `settings` —— 三库本就同构，直接合并（key 冲突加前缀 `toolbox.` / `chemeln.` / `huanghe.`）

#### 4.5.2 字段冲突处理规则

| 冲突类型 | 处理方式 |
| --- | --- |
| **同义异名**（mol_weight/mw、note/notes、steps/procedure） | 统一到目标名，迁移时 `SELECT` 时 `AS` 重命名 |
| **同名不同义**（project TEXT vs project_id INT） | **两者都保留**：`project_id` 为权威 FK，`project` 冗余保留原文本；迁移时按文本去重建 `projects` 表再回填 FK |
| **同名不同类型**（status 枚举） | 查表映射，见 2.2；映射表落库 `status_map` 便于审计 |
| **语义不同**（materials vs compounds） | 合并为超集表；`supplier/batch_no/location` 拆到 `compound_sources` |
| **默认值冲突**（category: general vs project） | 统一默认 `general`，迁移时保留原值（黄河原值本就 general，合迹原值 project 不改） |
| **NOT NULL 冲突**（黄河 status NOT NULL vs 合迹可空） | 目标表统一 NOT NULL + DEFAULT，迁移时空值填默认 |
| **FTS5 索引** | **迁移后全部重建**（`INSERT INTO fts(fts) VALUES('rebuild')`），不迁移索引内容 |
| **触发器**（ai/ad/au） | 重建索引时一并重建触发器 |
| **自增主键冲突** | 迁移时**重排 id**（新库自增），原 id 存 `source_id`，`source_app` 标记来源 → 保证可回溯、可回滚 |

#### 子 webview 嵌入方案（已实测，替代 iframe）

**2026-10-22 实测结论**：Tauri 2 的 `Window::add_child` **可以在同一个桌面窗口内创建原生子 webview**，
用它加载 chemELN 的 HTTP 页面可行。这比 iframe 更优（无 postMessage 同源限制、无双滚动条、无 iframe 沙箱）。

**原型实测证据**（真实编译运行，非文档推断）：

| 验证项 | 结果 |
| --- | --- |
| `Window::add_child` 创建子 webview | ✅ 成功（`child webview created, label=chem`） |
| 子 webview 加载 `http://127.0.0.1:8765/static/index.html` | ✅ 成功（`PAGE LOADED: url=http://127.0.0.1:8765/static/index.html`） |
| 窗口内实际渲染出两个 webview | ✅ `EnumChildWindows` 枚举到 **2 个 `WRY_WEBVIEW` 控件**（主 1200×800 + 子 1200×700） |
| Rust → 子 webview `eval()` 注入 JS | ✅ 12/12 次全部返回 `Ok` |
| 是否需要新增 crate | ❌ **不需要**，`add_child` 是 tauri 2.11.6 自带 API |

**必须注意的三个约束**（实测踩到）：

| # | 约束 | 证据 | 应对 |
| --- | --- | --- | --- |
| 1 | **`add_child` / `WebviewBuilder` 需要 `unstable` feature** | 编译报错 `no WebviewBuilder in the root` → `configured out ... gated behind the 'unstable' feature` | `Cargo.toml` 加 `features = ["unstable"]`。注意这意味着**依赖 tauri 的 unstable API**，升级大版本时需复核 |
| 2 | **`add_child` 定义在 `tauri::Window` 上，不是 `WebviewWindow`** | 编译报错 `no method named add_child found for struct tauri::WebviewWindow` | 用 `app.get_window("main")` 而非 `get_webview_window()` |
| 3 | **子 webview 的远程 origin 无法调用 Tauri 自定义命令** | 源码 `is_local_url()`：只认 `tauri://` 协议或 `devUrl`/`frontendDist` 相对路径；`http://127.0.0.1:8765` 属 remote origin → 需显式 `remote` capability | **主壳与子 webview 之间不要走 Tauri IPC**。改用：<br>① 主壳 → 子 webview：Rust `webview.eval()`（实测可用）<br>② 子 webview → chemELN 后端：直接 `fetch('/api/...')`（同源，无需桥）<br>③ 子 webview → 主壳：`postMessage`（同源问题不复存在，因为都在本机） |

**额外发现**：`on_page_load` 对子 webview **触发不可靠**（实测有时触发、有时不触发，且与页面实际加载状态不同步）。
→ **不要依赖 `on_page_load` 做初始化**。改用「Rust 侧定时 `eval` 探测就绪」或
`initialization_script`（但注意：源码注释明确 `initialization_script` **只对 custom protocol 生效**，
远程 URL 下改用 `onPageStarted` 且不保证早于其他脚本）。

**推荐通信拓扑**（绕开所有上述限制）：

```
┌─ Tauri 主进程 (Rust) ────────────────────────────────┐
│  管理子 webview 生命周期、eval 注入、端口分配            │
└───────────────┬───────────────────────────────────────┘
                │ eval("fetch('/api/...')")  ← 同源，直连后端
                ▼
┌─ 子 webview（chemELN 前端，http://127.0.0.1:8765）──┐
│  前端零改动：现有 fetch('/api/...') 天然同源             │
│  令牌：api.js 调 /api/session 引导 → 带 X-ChemELN-Token │
└───────────────┬───────────────────────────────────────┘
                │ fetch（同源 + header 带令牌）
                ▼
┌─ Python 后端（FastAPI + RDKit）─────────────────────┐
│  绑 127.0.0.1（已加固）· AccessGuard 校验令牌           │
└───────────────────────────────────────────────────────┘

主壳 ↔ 子 webview 双向：postMessage（同源，targetOrigin 显式指定）
主壳 → 数据层：Rust 直连统一 SQLite
主壳 → 后端：读 token 文件或用 CHEMELN_TOKEN 环境变量注入
```

> **P0.5 已把通信拓扑所需的鉴权机制落地**（2026-10-22 完成）：
> 后端现在要求会话令牌，主壳可用 `CHEMELN_TOKEN` 环境变量注入，
> 或直接读 `%APPDATA%\ChemELN\.session_token`；
> 子 webview 侧由 chemELN 前端自带的 `/api/session` 引导完成，**前端零改动**。

> 关键洞察：**chemELN 前端完全不用改代码**。
> 它现在的 `fetch('/api/...')` 在子 webview 里是同源请求，直连后端；
> 主壳要调用它的能力，用 `eval()` 注入即可；主壳要展示统一数据，用 Rust 直连数据库，
> 不经过前端。

#### 备选：iframe 方案（若不想用 unstable feature）

若不愿引入 `unstable` feature，退回 iframe（主 webview 内的 `<iframe src="http://127.0.0.1:8765/static/index.html">`）。
实测前提已验证：
- `api.js` 15 处调用**全部**为 `/api/...` 根绝对路径（相对路径 0 处）→ iframe 在 `/static/index.html` 下解析正确
- `index.html` 资源引用全为 `/static/...` 绝对路径
- `app.js` 是**纯状态机路由**（`state.view` + `render()`），**完全不碰 `history`/`location`** → 无深链 404 问题

| 维度 | 子 webview | iframe |
| --- | --- | --- |
| 稳定性 | 需 `unstable` feature（上游可能变） | 纯 Web 标准，零风险 |
| 通信 | Rust `eval` 直达，无同源限制 | `postMessage`，需处理 origin |
| 渲染 | 原生控件，集成度高 | 有 iframe 边框/滚动条问题 |
| 高度自适应 | 需手动 resize | 需手动 resize |
| 依赖稳定性 | ⚠️ 绑定 tauri unstable API | ✅ 不依赖框架版本 |

**建议**：优先子 webview，但把 iframe 作为降级方案预留（`unstable` 编译失败时自动切换）。


#### iframe 嵌入的可行性验证（已实测代码）

| 检查项 | 结论 |
| --- | --- |
| **API 路径解析** | ✅ `api.js` 15 处调用**全部**为 `/api/...` 根绝对路径（相对路径 0 处）。iframe 源为 `http://127.0.0.1:<port>/static/index.html` 时，`fetch('/api/experiments')` 解析为 `http://127.0.0.1:<port>/api/experiments` —— **正确** |
| **静态资源路径** | ✅ `index.html` 中 `href`/`src` 全部为 `/static/...` 绝对路径（CSS/JS/logo 全部），不受 iframe 层级影响 |
| **SPA 深链** | ✅ **无风险**。实测 `frontend/js/app.js` 是**纯状态机路由**（`state.view` + `render()`），**完全不碰 `history`/`location`**，页面状态不体现在 URL 上 → iframe 内不存在深链 404 问题 |
| **iframe 初始 src** | 用 `http://127.0.0.1:<port>/static/index.html`（静态资源挂载点即前端根）；不要用 `/`，避免与 SPA catch-all 的职责冲突 |
| **主壳→iframe 导航** | 由于 URL 不承载状态，主壳想控制 iframe 显示哪一页，必须走 `postMessage` 调 iframe 内的 `navigate(view)` 方法（chemELN 侧加约 20 行暴露即可） |
| **视口尺寸** | iframe 高度需主壳侧按内容自适应（`postMessage` 上报 `document.body.scrollHeight`），否则会出现双滚动条 |

**结论**：iframe 方案**技术上可行且风险低**。现有 chemELN 前端已经是「根绝对路径」写法（无需改路径），且是纯状态机路由（无深链问题）。需注意的只有两点：主壳需通过 `postMessage` 调 iframe 内的 `navigate()` 来控制页面、以及 iframe 高度自适应。
